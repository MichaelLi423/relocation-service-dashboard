## 2. 业务目标

1. 搬迁负责人通过工作台完成从进单、联系客户、安排运输公司与工程师、录入单据、记录执行状态到费用申请的全流程控制。
2. 工作台用于记录关键时间点信息、把控搬迁项目流程、回顾工作情况。
3. 工作台记录并统计各业务对象的工作量（开单、Ship-to 申请、损坏维修备件、二维码申请、序列号地址更新、掉票等），支撑季度汇报类统计报表。

## 3. 首版范围

### 3.1 范围内

1. 首版记录搬迁、认证、单寄备件、PM 四类开单业务及其工作量。
2. 只有搬迁业务建立搬迁项目，并进入完整的进单、执行、验收和掉票生命周期。
3. 首版仅由搬迁负责人使用并维护工作台数据；应用提供单一本地应用账号作为访问门槛，首次启动必须创建用户名与密码、后续启动需登录，无多账号、注册、角色与权限管理（见第 12 章）。
4. 涵盖进单与未进单先执行、开单、搬迁批次与物流、Ship-to 与序列号地址更新、损坏维修与备件、服务二维码与二维码申请、项目提醒、掉票等子流程。
5. 提供进单金额、掉票金额与次数、开单量、损坏维修记录数量与备件金额及合同占比、物流费用与物流费用合同占比、Ship-to 申请工作量、二维码申请工作量、序列号地址更新记录数等统计与报表；报表支持手工选择月份区间并实时更新，支持 Excel（.xlsx）、PNG、PDF 三种导出。
6. 支持对现有 Excel 历史记录的存量数据导入；导入统一经登录后「数据管理 → 历史数据导入」向导执行（模板下载 / 文件选择 / Excel 矩形粘贴 / 七类声明 / 草稿修订 / 错误冲突 / 完整校验与封存 / 原子提交 / 中断恢复），不再提供工作台外的命令行入口（历史说明见第 10 章）。

### 3.2 明确不做

| 事项 | 说明 |
| --- | --- |

| 多人账号、注册、角色与权限管理及项目负责人字段 | 首版仅提供单一本地应用账号（首次启动初始化、后续登录、忘记密码恢复码重置），不支持新增第二个账号、注册、自助新增用户、角色与权限管理；不设项目负责人字段（已确认） |
| 销售通知记录 | 销售通知不再作为工作台记录项（已确认） |
| 邮件自动解析与外部消息渠道提醒 | 外部业务事实由搬迁负责人手工记录；项目提醒仅在工作台内展示，首版不做邮件自动解析与外部渠道提醒（已确认） |
| 二维码生成与外部内容实现 | 工作台只按仪器手工标记"二维码是否申请"，不保存二维码地址（已确认） |

| 财务审批、驳回与客户回款状态追踪 | 掉票只记录发生日期与金额（已确认） |
| 验收报告附件或外部链接存储 | 验收仅记录"已有验收报告"及报告形成日期（已确认） |
| 认证、单寄备件和 PM 的完整生命周期 | 首版只记录开单信息和工作量，不复用搬迁项目生命周期（已确认） |
| 独立备件申请 | 备件申请信息并入损坏/维修事项（记录备件申请日期与备件处理状态），不提供独立备件申请对象/入口（已确认） |
| 自动生成待办/提醒 | 系统不根据缺失字段自动生成待办或提醒；项目提醒完全由负责人手工维护（已确认） |

## 4. 角色与协作边界

1. 搬迁负责人是首版唯一的数据使用与维护角色，也是唯一本地应用账号的使用者（首次启动初始化账号、后续启动登录，无远程认证，见第 12 章）；外部业务事实（经理批复、工程师执行、运输公司信息、合同金额等）由负责人录入或确认，系统自动记录或迁移导入的数据不视为手工录入；手工录入事实与工作量责任人归属当前已登录的本地应用账号，动作记录持久化账号内部 ID 与当时用户名快照。
2. 销售：无独立账号、审批入口或数据维护入口；首版不记录销售通知（已确认）。
3. 经理：对"未进单先执行"进行批复；批复信息（批复、原因、缺失项）由搬迁负责人手工记录，经理无独立审批入口。
4. 工程师：上门执行信息由搬迁负责人记录；工程师无独立账号或数据维护入口。
5. 运输公司/供应商：报价与费用信息由搬迁负责人维护；供应商无独立账号或数据维护入口。
6. 首版按单个搬迁负责人设计，仅提供单一本地应用账号，不设项目负责人字段，不实现多人账号、数据权限与角色权限管理；各项工作量指标的责任人取对应动作记录中持久化的当前登录本地账号（账号内部 ID 与用户名快照），不依赖项目负责人字段。

## 5. 领域对象与关系

术语定义以 CONTEXT.md《搬迁服务》为准，本节只描述对象间关系，不重复整个词汇表。

### 5.1 核心对象

- 客户：以客户名称为唯一业务标识（去除首尾空白后全局唯一），同一客户名称可关联多个不同 ECC 搬迁项目；系统内部可使用技术引用 ID，但对外唯一标识以客户名称为准。
- 合同：与搬迁项目一一对应的合同；一份合同只对应一个搬迁项目；待进单阶段合同可空（可不关联合同），正式进单前必须补齐合同；记录合同开始日期与合同截止日期、合同 USD 含税金额（允许为 0）。
- 搬迁项目：与合同边界一致的整体服务范围，统一验收、统一核算；与合同共用 ECC；记录区域、旧址与新址联系人、默认旧址与新址、计划上门与计划运输日期、场地确认、实际装机完成日期等。
- ECC：一份合同及其唯一搬迁项目共用的全局唯一业务编号；正式进单后必填，未进单先执行阶段可暂用系统临时编号。
- 搬迁批次：同一搬迁项目内、同一次运输安排下的一组搬迁仪器，批次与物流费用合并为一次记录；一个项目可有多个批次；记录计划运输日期、运输公司（可选）、费用登记日期、合同预算价与物流成交价（人民币，均必填且大于 0）；物流成交价即最终实际物流费用。
- 搬迁仪器：按序列号识别的一台仪器；记录仪器名称（必填）、型号（选填）、UPS 是/否、所属搬迁批次、"二维码是否申请"（手工是/否）及拆装进度。非空序列号在同一合同/其唯一搬迁项目内不得重复、跨合同可重复；允许无序列号占位，暂定数量不生成虚拟仪器。
- 上门活动：一次实际到访的现场工作记录；一次活动可由多名工程师参与并处理多台搬迁仪器，工作内容可包含拆机、装机、维修、其他；拆机工作事实明确记录拆机状态及拆机开始/完成日期，其他工作类型记录各自状态与日期。
- 开单记录：实际生成一份搬迁、认证、单寄备件或 PM 服务单据的业务记录；记录开单日期、服务单号、开单类型、工程师、客户单位，备注可选；开单不等同于正式进单。
- 掉票记录：项目验收后按 ECC 向财务提交可确认金额的动作记录；掉票不可物理删除，撤销后为终态，禁止编辑、重复撤销或重新激活，更正需新增有效掉票。
- 损坏/维修事项：一台搬迁仪器的一次运输损坏及其后续处理的整体记录；一个事项记录损坏原因、处理状态、单个备件的备件号/数量/金额、备件申请日期、备件处理状态（待提交、处理中、已到件、已使用）及维修过程备注；一个事项只对应一个备件，多个备件需分别建立事项；仅"已使用"状态的备件计入维修费用与合同占比。
- Ship-to：一处搬迁目的地址主数据；创建后不可修改，唯一编号为 Account ID（不是客户主账号）。
- Ship-to 申请：为系统外新址地址申请新增 Ship-to 的业务记录；只记录客户名称与新址地址，不关联搬迁仪器，不保存地址快照；状态线性流转：待提交 → 处理中 → 已完成，不支持退回或取消。
- 序列号地址更新：逐台登记搬迁仪器序列号实际关联新址的记录，含客户名称、新址地址、序列号、Account ID 与更新日期；不创建、修改或删除 Ship-to 主数据。
- 服务二维码：按搬迁仪器分别生成的外部二维码，内容为公司统一定制；工作台不保存二维码地址，仅由负责人按仪器手工标记"二维码是否申请"。
- 二维码申请：独立模块中的申请记录，保存申请人、申请日期与一个或多个申请类型（多选）；不关联搬迁仪器或搬迁项目，不设状态流转。
- 项目提醒：负责人为每个搬迁项目手工维护的当前提醒信息，包含一个当前提醒日期与备注内容，可编辑或清除，不保存提醒完成历史；系统不根据缺失字段自动生成提醒。
- 本地应用账号：首版唯一的本地登录账号；首次启动必须创建用户名与密码，创建后禁止新增第二个账号；手工录入事实与工作量责任人归属当前登录账号，动作记录持久化账号内部 ID 与当时用户名快照（历史统计不因以后改名变化）。

### 5.3 汇总展示原则

1. 搬迁批次和搬迁项目只汇总展示所涉及的 Ship-to，不重复维护唯一的批次级或项目级地址。
2. 搬迁项目汇总各批次的运输安排和物流费用，不重复维护项目级物流明细。
3. 认证、单寄备件和 PM 开单记录独立保存，不进入搬迁项目生命周期。

## 6. 业务事件与项目生命周期

### 6.1 业务事件

- 正式进单（搬迁负责人确认接手项目）
- 开单（实际生成服务单据）
- 首次上门活动开始、首次搬迁批次开始运输
- 实际装机完成
- 验收报告形成（标记已有验收报告并填写报告形成日期）
- 掉票（按 ECC 向财务提交可确认金额）
- 项目取消

### 6.2 主状态与标签

1. 搬迁项目主状态依次为：待进单、待执行、执行中、待验收、待掉票、已完成；终止的项目标记为已取消或已转单。
2. 负责人可以直接选择/人工调整项目主状态（TBD-09）；系统在保存时校验合法性（合法状态、取消约束、金额闭环约束）。
3. 以下自动触发仍生效，负责人人工选择不得覆盖：录入实际装机完成日期自动进入待验收（TBD-07）；标记已有验收报告并填写报告形成日期自动进入待掉票；待掉票/已完成之间按累计掉票金额与最终可确认金额自动重算（TBD-11）。
4. "未进单先执行"等异常作为独立标签，可与主状态同时存在（存在该标签时主状态保持待进单）。
5. 未进单项目与已进单项目在界面中使用明确不同的颜色/视觉标识（TBD-08）。
6. "已完成"表示掉票金额闭环（见 6.4）。
7. 已取消项目不可恢复；如需继续工作，需重新新增项目。
8. 已转单为终态：由负责人人工进入，转单后不再自动推进；人工进入后不可再离开，自动触发与事实重算均不得将其改出终态。已转单与已取消同等排除活跃项目、收入、掉票与项目管道统计，并同等冻结金额与掉票修改。

### 6.3 状态转移条件

| 当前状态 | 触发条件 | 目标状态 |
| --- | --- | --- |
| 待进单 | 正式进单（补齐合同、客户单位、搬迁范围）且尚未发生实际执行活动 | 待执行 |
| 待执行 | 首次上门活动开始，或首个搬迁批次开始运输；仅完成排期、工程师或运输公司安排不算开始执行 | 执行中 |
| 执行中 | 负责人录入实际装机完成日期 | 待验收 |
| 待验收 | 标记已有验收报告并填写报告形成日期；不需要客户确认 | 待掉票 |
| 待掉票 | 累计掉票金额达到项目最终可确认金额 | 已完成 |
| 待掉票 / 已完成 | 掉票或最终可确认金额修改后，按累计金额与最终可确认金额在两者之间重算 | 按重算结果取待掉票或已完成 |
| 任一未取消状态 | 项目无任何掉票历史（含已撤销），并记录取消日期与原因 | 已取消 |
| 任一非终态 | 负责人人工选择转单（终态，不需记录掉票历史条件） | 已转单 |

> 注：计划上门日期、计划运输日期与场地确认不触发主状态流转，仅用于工作台展示。主状态可由负责人人工调整（TBD-09），上述自动触发与取消约束在保存时校验。未进单先执行项目在正式进单后由负责人人工确定主状态，系统不按已发生事实自动跳转（TBD-08）；实际装机完成、验收报告、金额闭环等已明确自动触发除外。

### 6.4 "已完成"的判定口径

1. 项目"已完成"表示掉票金额闭环：累计掉票金额达到项目最终可确认金额即进入已完成。
2. 未完成的损坏维修、未完成的 Ship-to 申请、仪器"二维码是否申请"未标记等事项**不阻塞**项目的进单、执行、验收、掉票或完成。
3. 项目验收后仍允许报修/维修，且不影响验收、待掉票或完成状态（TBD-07）。
4. 首版不追踪财务审批、驳回或客户回款状态。

### 6.5 取消

1. 无任何掉票历史（含已撤销掉票）的任一未取消主状态均可取消；取消时必须记录取消日期和原因。
2. 存在任何掉票历史（含已撤销掉票）的项目禁止取消。
3. 已取消项目不可恢复；如需继续工作需重新新增项目；已取消状态期间禁止修改合同金额、最终可确认金额与掉票记录。
4. 已取消项目保留已经发生的上门活动、物流和费用记录；真实物流费用与损坏维修备件金额作为实际成本保留并计入对应统计，同时标记为已取消项目。
5. 已取消项目排除在项目管道、进单金额（收入）、掉票金额与掉票次数及金额闭环等收入与掉票指标之外。

### 6.6 未进单先执行

1. 核心信息未齐时，经经理批复可在正式进单前优先安排上门；在原搬迁项目上记录经理批复、原因及缺失项，主状态保持待进单。
2. 正式进单后由负责人人工确定主状态；系统不按已发生事实自动跳转（实际装机完成、验收报告、金额闭环等已明确自动触发除外），且在原搬迁项目上完成进单，不新建项目。

### 6.7 时间口径（全局约定，已确认）

1. **所有业务时间仅记录业务日期 yyyy-mm-dd**（不含时分秒与时区偏移）：进单日期、开单日期、掉票日期、撤销日期、取消日期、费用登记日期、备件申请日期、登记日期、更新日期（序列号地址更新）、申请日期（二维码申请）、首次提交日期、完成日期（Ship-to 申请）、到访日期、工作事实开始/完成日期、计划上门/运输日期、实际装机完成日期、提醒日期等一律以业务日期表达。
2. **审计/技术时间保留精确 ISO**（含时区偏移）：系统创建时间、动作记录时间、导入运行时间、记录最后修改时间等只用于审计或技术追溯，不参与业务归属与报表月份归属；进单日期与系统创建时间分开记录。
3. **历史值按升级时本机业务时区转换为日期**：历史数据导入或既有数据升级时，源日期时间按升级时本机业务时区转换为业务日期（yyyy-mm-dd）后写入业务字段；导入运行时间仅进审计，绝不替代源业务日期。
4. **报表/月度归属按业务日期**：进单金额、掉票金额与次数、开单量、损坏维修、物流费用、Ship-to 申请、二维码申请、序列号地址更新等所有时间归属均以对应业务日期所属月份计算。
5. **界面使用日期控件**：工作台录入与筛选界面为业务日期字段提供日期控件（yyyy-mm-dd），不使用自由文本或时间选择器录入业务时间。

## 7. 子流程

### 7.1 进单与未进单先执行

**正式进单日期规则**

1. 正式进单是搬迁负责人补齐必要信息并正式确认接手搬迁项目的业务事件，与开单是两个不同事件。
2. 进单日期在正式进单时必填，默认取当天，允许补录或修正；负责人填写的进单日期保持其填写值，不以当天默认值覆盖；待进单或未进单先执行阶段可空。
3. 进单日期与系统创建时间（审计/技术时间，精确 ISO）分开记录，并作为进单统计口径。
4. 正式进单至少需要关联合同、客户单位并明确搬迁范围；任一缺失拒绝进单。正式进单前必须补齐合同；待进单阶段合同可空（可不关联合同），系统不强制在待进单时创建空合同草稿（项目稳定内部 ID 与临时编号仍保留）。
5. 最终搬迁地址、工程师、运输公司和费用允许在进单后补充。
6. 核心信息未齐时，经经理批复可在正式进单前优先安排上门；在原搬迁项目上标记"未进单先执行"，记录经理批复、原因及缺失项。
7. 后续在原项目上补齐正式进单所需核心信息并完成进单，不新建正式项目；进单后由负责人人工确定主状态（见 6.3 注）。

**新建项目四步向导**

- **步骤 1 基本信息**：进单日期、区域、旧址联系人、新址联系人、合同开始日期与合同截止日期；不包含项目负责人或销售通知时间。合同截止日期不得早于合同开始日期，否则拒绝保存并提示。
- **步骤 2 搬迁范围**：旧址地址、新址地址、仪器名称（必填）、型号（选填）、UPS 是/否；不保存 Ship-to 地址快照。
- **步骤 3 执行准备**：计划上门日期与计划运输日期（分开记录）、场地确认、实际装机完成日期、服务单号（选填）。允许留空后补的字段在保存时不无提示丢失未填写内容；实际装机完成日期在执行前为空不触发任何状态流转或提醒。
- **步骤 4 确认方式**：展示录入摘要，支持保存为待进单、正式进单、未进单先执行三个确认路径；保存为待进单时分配内部 ID 与系统临时编号，不强制建立合同草稿。

**步骤 3 服务单号与开单创建**

- 服务单号选填；填写并保存且已选定参与工程师时，项目与自动创建的关联该搬迁项目的搬迁开单记录在同一保存操作中一并保存（原子保存），实际生成日期默认取当天，备注可空并允许后补。
- 填写单号但未选定工程师时，拒绝保存整个向导（项目本身也不保存）并就地提示先补齐工程师；不填写单号时不创建任何开单记录。
- 实际装机完成日期录入后，项目主状态自动进入待验收；计划日期与场地确认不触发状态流转。

### 7.2 开单记录

1. 开单与正式进单是两个独立业务事件；开单不影响项目进单状态与主状态。
2. 开单记录区分搬迁、认证、单寄备件、PM 四类业务。
3. 搬迁开单关联对应搬迁项目；认证、单寄备件和 PM 开单独立保存，不进入搬迁项目生命周期。
4. 非空服务单号全局唯一，不同业务类型共用同一唯一空间。
5. 认证、单寄备件与 PM 开单至少记录开单日期、服务单号、开单类型、工程师、客户单位；备注可选。开单日期未填默认当天。
6. 开单工作量按唯一服务单号计数，同一服务单关联多名工程师或多次上门时仍只计一次，并按四类业务类型分组。

### 7.3 搬迁批次与物流

1. 运输公司记录在搬迁批次上；同一搬迁项目的不同批次可使用不同运输公司；运输公司保持可选。
2. 搬迁批次与物流费用合并为一次记录：批次创建时同时必填费用登记日期、合同预算价与物流成交价（人民币，均必须大于 0）；物流成交价即该批次最终实际物流费用，不再单独录入"实际物流费用"金额；批次创建不再保留原价/折后价独立报价层。
3. 费用登记日期必填并默认当天，首次登记后决定归属月份；后续从批次编辑修改运输信息与合同预算价、物流成交价时，费用登记日期不修改、归属月份不变。
4. 物流成交价大于合同预算价时显示警告但允许保存，不自动创建项目提醒、不阻塞批次运输或项目流转。
5. 项目汇总各批次的运输安排和物流费用。
6. 物流费用合同占比：物流成交价（即最终实际物流费用）按人民币记录，按固定汇率 1 USD = 7.2 RMB 折算为 USD 后，除以最新合同 USD 含税金额展示；合同金额为空或 0 时不可计算并提示。
7. 历史导入仍兼容旧"预算价格/成交价格/实际物流费用"三列数据（底层保留兼容），但该三列不是当前录入模型；历史批次缺费用视为异常数据，不提供独立补录入口。

### 7.4 Ship-to 与 Ship-to 申请、序列号地址更新

**Ship-to 主数据**

1. 每处搬迁目的地址以 Ship-to 表达，唯一编号为 Ship-to ID（沿用现有字段名 Account ID），不是客户主账号；创建后不可修改，全部引用保持稳定。
2. 目的地址发生变化时重新申请新的 Ship-to，不更新或覆盖原记录。

**Ship-to 申请**

3. 系统中不存在目的 Ship-to 时，按同一客户、同一新址地址创建一条 Ship-to 申请；申请只记录客户名称与新址地址，不关联搬迁仪器、不保存结构化地址快照；客户或新址地址不同分别创建申请。
4. 申请创建时 Account ID 可空；由系统外完成流程返回后由负责人补入，补入的 Account ID 全局唯一（不得与已有 Ship-to 重复），补入后申请进入已完成并记录完成日期；申请进入已完成前 Account ID 必填。补入的 Account ID 创建/对应不可变的 Ship-to。
5. 申请状态线性流转：待提交 → 处理中 → 已完成，不支持退回或取消。每条申请在首次实际提交时计一次工作量，待提交草稿不计，退回重提不重复计数（线性状态下"退回重提"不发生）。
6. 申请未完成时只显示为独立提醒信息，不阻塞搬迁项目的进单、执行、验收、掉票或完成；系统不自动生成"Ship-to 申请未完成"提醒。

**序列号地址更新**

7. 搬迁仪器实际迁往新址地址时，逐台登记一条序列号地址更新事实，记录客户名称、新址地址、序列号、Account ID 与更新日期；一台仪器可有多条更新事实表达多次地址变化。
8. 项目级新址地址仅作为默认计划，不自动成为每台仪器的实际关联新址；仪器实际关联新址以该仪器最近一条更新事实的新址地址为准。
9. 更新事实不得创建、修改或删除 Account ID 对应的不可变 Ship-to。
10. 更新日期必填、默认当天并可补录历史日期；客户名称、新址地址、序列号、Account ID 与更新日期为非空必填字段；序列号须与登记的搬迁仪器一致，不引入未确认的序列号格式约束。
11. 系统提供更新事实列表，支持按客户、新址地址、序列号、Account ID 或更新日期筛选，并按更新日期所属月份计数。

### 7.5 损坏、维修与备件

1. 一台搬迁仪器的一次运输损坏建立一个损坏/维修事项并关联该仪器；一个事项仅包含一个备件（备件号、数量、金额），同一损坏涉及多个备件时按备件分别建立多个事项，一个事项不得承载多个备件。
2. 事项记录字段：损坏原因、处理状态、备件号、数量、金额、币种、备件申请日期、备件处理状态、维修过程备注；维修上门等处理过程记录在维修过程备注中。
3. 事项处理状态为未处理、处理中、已修复、已关闭未修复；选择已关闭未修复时必须记录原因。
4. 备件处理状态为待提交、处理中、已到件、已使用；仅"已使用"状态的备件计入维修费用与合同占比。备件申请日期与备件处理状态直接记录在事项内，不引入独立备件申请对象。
5. 备件金额保留原币金额与币种（仅 USD 或 RMB）；RMB 金额固定按 1 USD = 7.2 RMB 折算为 USD 用于维修费用占比，不随年度变化，首版不接入实时汇率服务。金额必须有值且大于 0。
6. 合同 USD 含税金额为空或 0 时，可以登记损坏（建立损坏/维修事项），但禁止开始/完成维修，也禁止将备件处理状态标记为"已使用"；补齐正数合同金额后才允许这些操作（TBD-15）。该约束同样作用于"维修"类上门活动与事项的关联。
7. 损坏/维修事项独立于搬迁项目生命周期；未完成处理不阻塞项目的进单、执行、验收、掉票或完成，并可在这些阶段之后继续处理。
8. 维修报表按事项记录数量、单条记录的备件金额及合同占比统计：合同占比 = 单条记录金额 ÷ 合同 USD 含税金额；合同金额为空或零时不可计算并明确提示；占比超过 100% 允许如实显示并给出警告。
9. 维修上门活动与损坏/维修事项为多对多关联：一次"维修"类上门活动可关联多个事项、同一事项可被多次维修上门关联；关联时校验该事项所属仪器属于该活动的仪器集合，校验失败拒绝关联且既有关联保持不变；该关联仅为引用，维修过程仍记录在事项备注中。

### 7.6 服务二维码与二维码申请

1. 每台搬迁仪器的"二维码是否申请"为负责人手工维护的是/否字段；不保存二维码地址（URL），不由二维码申请记录推导，不自动创建项目提醒，不阻塞上门、运输或项目状态流转。
2. 二维码内容由公司统一定制，包含拆机报告、装机报告和序列号收集模块。
3. 二维码申请作为独立模块维护，与搬迁仪器和搬迁项目解耦：每条申请记录保存申请人、申请日期与一个或多个申请类型（多选），申请类型沿用九类固定代码（A、B、C、D、仅打包搬运精密仪器、OEM 设备、临时标签、项目验收单、物流管理）；申请不设状态流转。
4. 二维码申请工作量按申请记录 × 去重后的选中类型计数：一条记录内每个去重后的选中类型各计一次，同一条记录内相同类型只计一次，不同申请中的相同类型分别计数；重复申请保留完整历史。
5. 项目快速记录入口不含二维码申请；二维码申请通过独立模块入口维护。

### 7.7 项目提醒

1. 搬迁负责人为每个搬迁项目手工维护一个当前项目提醒：包含一个当前提醒日期与备注内容；提醒可编辑或清除，不保存提醒完成历史。
2. 系统不根据任何缺失字段自动生成提醒（原七类自动标准待办整体删除）；"自定义待办"概念并入项目提醒，不再单列。
3. 提醒到期分类按提醒日期显示临期、今日到期或已逾期：截止日当天归为今日到期，超过截止日归为已逾期；临期窗口由负责人配置，未配置时默认未来 7 个自然日。
4. 物流成交价高于合同预算价、二维码未标记、Ship-to 申请未完成等情形均不自动创建项目提醒，负责人如需跟进可手工维护提醒。
5. 首版仅在工作台内展示项目提醒，不接入邮件、企业微信等外部消息渠道。
6. 主工作流为"项目提醒快速处理 + 高密度项目队列"。

## 8. 金额与币种规则

### 8.1 金额表达与正数规则

1. 所有金额以两位小数的十进制定点表达，保存与统计按四舍五入处理，全程不采用二进制浮点参与金额计算；金额不得为负数。
2. 仅"合同 USD 含税金额"允许为 0；其他录入金额（最终可确认金额、掉票金额、批次合同预算价/物流成交价、损坏维修备件金额等）有值时必须大于 0，不得为 0 或负数；不允许 0 金额闭环（如 0 元掉票、0 元最终可确认金额）。
3. 合同金额为 0 时，正式进单时最终可确认金额不能默认成 0，必须另行录入大于 0 的值。

### 8.2 合同金额

1. 合同 USD 含税金额由搬迁负责人手工录入；可直接覆盖当前值修改，不保存正式合同变更对象/历史，不要求记录原因（TBD-20）。
2. 正式进单时保存合同 USD 含税金额快照，该快照仅用于进单金额统计；后续合同金额覆盖不改写历史快照，最新合同金额用于当前项目展示、维修费用占比与物流费用合同占比。
3. 合同金额覆盖不影响最终可确认金额：最终可确认金额保持原值，不随合同金额覆盖而同步（TBD-20）。

### 8.3 项目最终可确认金额与掉票

1. 项目最终可确认金额默认取合同 USD 含税金额，允许搬迁负责人调整；最终可确认金额不得低于累计掉票金额。合同金额为 0 时正式进单的最终可确认金额必须另行录入大于 0 的值，不能默认成 0。
2. 新增掉票记录后累计金额不得超过项目最终可确认金额；确需增加时应先调整最终可确认金额，再登记掉票。
3. 掉票支持分次记录，每次分别记录掉票日期和金额；掉票日期和金额允许直接覆盖修改，不保留旧值和更正原因，但自动记录最后修改时间（审计/技术时间，精确 ISO），并据此重新计算统计结果。
4. 掉票记录不可物理删除，只能撤销；撤销必须记录撤销日期和原因；撤销后为终态，禁止编辑、重复撤销或重新激活，更正需新增有效掉票；撤销后该记录不再计入掉票金额与掉票次数，并重新计算统计结果与项目状态。
5. 项目已处于待掉票或已完成时，掉票或最终可确认金额修改后按累计金额与最终可确认金额在两者之间重算；项目未处于待掉票或已完成时，金额修改不改变主状态。
6. 项目处于已取消状态期间，禁止修改合同金额、最终可确认金额与掉票记录。

### 8.4 备件币种与折算

1. 损坏/维修事项的备件金额保留原币金额与币种（仅 USD 或 RMB）。
2. RMB 备件金额固定按 1 USD = 7.2 RMB 折算为 USD 用于维修费用占比，不随年度变化；首版不接入实时汇率服务，其他币种暂不支持。

### 8.5 物流费用合同占比

1. 物流费用合同占比 =（物流成交价（即最终实际物流费用）人民币按固定汇率 1 USD = 7.2 RMB 折算为 USD）÷ 最新合同 USD 含税金额。
2. 合同金额为空或 0 时不可计算并明确提示；占比超过 100% 允许如实显示并给出警告。

## 10. 历史数据导入

历史数据导入**只能**通过登录工作台后「数据管理 → 历史数据导入」向导执行（全部操作经
`import-wizard:*` 通道、会话守卫与受信窗口校验）；**不存在外部命令行入口**，自由文本
operator 与命令行已移除（历史说明见本章末「历史说明」）。

1. 向导是历史数据导入的唯一入口：登录后进入数据管理 → 历史数据导入，新建/继续草稿，
   下载当前版本空白模板、选择 Excel 文件（可在工作线程读取并取消）或从 Excel 矩形区域
   粘贴（确认首行为表头或业务数据），按七类逐类显式声明「有数据 / 本次无数据」。
2. 导入以 ECC 为项目/合同聚合主键：同一 ECC 下一个合同的全部执行数据聚合为一个搬迁
   项目；服务单号、Account ID、序列号用于子记录识别与冲突处理，不与 ECC 同级匹配项目。
   缺 ECC 的项目/合同执行数据在完整校验阶段报必填错误且该记录不可提交。
3. 合同字段以合同信息表为主要来源，执行字段以项目执行表为主要来源，开单、掉票等动作
   记录以工作量统计表为主要来源；供应商与物流费用历史记录分别以供应商表、物流公司
   信息费用表为来源（旧五源冻结映射；未知 sheet/列进入待人工映射或排除，不猜测）。
4. 记录识别以业务键（ECC、服务单号、Account ID、序列号）优先，无业务键时以来源 + 行号
   兜底；无法明确拆分的旧数据保留未分批状态并进入冲突清单。
5. 同一字段在多个来源中取值冲突时不自动覆盖，在向导中生成冲突清单由搬迁负责人选择
   候选或修正。
6. 不同源记录存在重复的非空服务单号时进入冲突清单，解决前该批次整批禁止提交。
7. 完整校验对目标必填字段缺失的行输出错误，错误定位到源文件、sheet、行号与缺失字段；
   负责人修正源数据或直接在网格修正后重新完整校验。
8. 存在目标必填字段缺失错误的记录不可提交；目标可选字段允许为空，缺失不构成错误。
9. 校验通过后生成 validation seal；提交前事务外创建并验证安全快照（快照失败零业务
   写入），单个立即写事务内复核封存并一次写入七类 + 来源审计 + 目标快照 + 运行审计 +
   对账；任一记录失败整体回滚，不产生部分数据；成功批次同源重跑不重复写入；已提交的
   错误数据仅通过修正后 forward-fix 纠正，不依赖反向回滚。
10. 历史项目状态由导入的事实经确定性规则重建；导入的业务事实标记为历史导入来源，
    **不计入登录账号的手工工作量**；运行审计（import_run）记录提交登录账号的内部 ID
    与提交时用户名快照，用于追溯草稿创建人与最终提交人。
11. 导入时间只作为审计字段保存，绝不替代源业务日期；源业务日期（掉票日期、开单日期、
     实际物流费用申请/登记日期、进单确认日期等）映射到对应业务字段并按升级时本机业务
     时区转换为业务日期，缺失时保留为空，不用导入时间填充；该业务日期为目标必填字段时
     由完整校验报错且该记录不可提交。
12. 覆盖新增字段或新增模块时不猜测映射（不按备注、相似文本或旧字段推断），无法明确
    映射的新增字段或模块进入冲突清单由负责人确认。
13. 导入后不存在"待补必填字段"流程，工作台不提供补录入口。

> **保护边界**：工作台数据库与导入工作区均为普通 SQLite 文件，**不加密**；登录账号只
> 控制界面访问，不能防止直接读取数据库文件。数据文件与备份的主要保护边界为
> **Windows 操作系统账户**（文件系统 ACL 与磁盘加密，如 BitLocker）。

> **历史说明**：早期文档与旧实现提供工作台外的迁移 CLI（`migrate-cli`，含 `--operator`
> 自由文本参数与 dry-run 命令）作为一次性存量迁移入口。该入口已删除：不再提供命令行
> 构建/预演/导入命令，打包产物不包含隐藏 CLI，历史数据导入统一经工作台向导执行。
> 本表第 1~13 条均以向导为唯一入口重新表述。

## 11. 数据校验与修改规则

1. 金额以两位小数的十进制定点表达并四舍五入，不得为负数；仅合同 USD 含税金额允许为 0，其他录入金额有值时必须大于 0（见 8.1）。
2. 合同 USD 含税金额由负责人手工录入并可直接覆盖修改；不保存正式合同变更对象/历史，不要求记录原因；覆盖不改写进单金额快照，不同步最终可确认金额。
3. 正式进单核心资料（合同、客户单位、搬迁范围）任一缺失拒绝进单；正式进单前必须补齐合同；合同金额为 0 时最终可确认金额不能默认成 0，必须另行录入大于 0 的值。
4. 向导步骤 3 填写服务单号时，参与工程师必填：未选定参与工程师则拒绝保存整个向导（项目本身也不保存）并就地提示先补齐工程师；填写且已选定参与工程师时项目与自动创建的搬迁开单同次保存，实际生成日期默认当天，备注可后补。
5. 合同截止日期不得早于合同开始日期，否则拒绝保存并提示。
6. 新增掉票记录后累计金额不得超过项目最终可确认金额；确需增加时先调整最终可确认金额。
7. 最终可确认金额不得低于累计掉票金额。
8. 掉票日期和金额允许直接覆盖修改；不保留旧值和更正原因，自动记录最后修改时间（审计/技术时间，精确 ISO）并据此重新计算统计结果；掉票只可撤销不可删除，撤销必须记录撤销日期与原因，撤销后为终态（禁止编辑、重复撤销或重新激活），更正需新增有效掉票。
9. 费用登记日期必填并默认当天，从批次编辑修改运输信息与合同预算价、物流成交价不改变费用登记日期与归属月份；物流成交价大于合同预算价时显示警告但允许保存，不自动创建项目提醒。
10. 损坏/维修事项选择"已关闭未修复"时必须记录原因；备件金额必须有值且大于 0；合同 USD 含税金额为空或 0 时禁止开始/完成维修、禁止将备件标记为"已使用"，补齐正数合同金额后才允许。
11. Ship-to 创建后不可修改；目的地址变化时申请新 Ship-to，不更新或覆盖原记录；Ship-to 申请状态线性流转（待提交 → 处理中 → 已完成），不支持退回或取消；Account ID 完成前必填、补入后全局唯一。
12. 序列号地址更新事实的客户名称、新址地址、序列号、Account ID 与更新日期为非空必填字段；序列号须与登记的搬迁仪器一致。
13. 项目取消必须记录取消日期和原因；存在任何掉票历史（含已撤销）的项目禁止取消；已取消项目不可恢复、禁止修改金额与掉票记录。项目转单后进入"已转单"终态（人工进入、转单后不再自动推进、不可再离开），与已取消同等排除活跃/收入/掉票/管道统计并冻结金额与掉票修改。
14. 正式进单后 ECC 必填；ECC 全局唯一，正式进单后的更正通过唯一性校验并自动记录最后修改时间。
15. 非空序列号在同一合同/其唯一搬迁项目内不得重复、跨合同可重复；运输开始前的改批保留改批历史（原批次、新批次、变更日期、登录账号归属），运输开始后禁止直接改批。
16. 客户名称为去除首尾空白后全局唯一的唯一业务标识；不记录客户外部编号。

## 12. 运行与持久化边界

以下为已确认的首版边界（TBD-16 已解决，对应 ADR `docs/adr/0001-windows-desktop-local-sqlite.md`），不属待确认项：

1. 首版仅个人使用，仅支持 Windows 桌面，以桌面应用形态运行（Electron + React + TypeScript）。
2. 全部业务数据持久化在本机 SQLite 数据库中；关闭并重新打开应用后数据保留。
3. 不接入远程数据库、云同步或外部业务系统；首版不向任何远程服务发送业务数据。
4. 应用提供**单一本地应用账号**作为访问门槛：首次启动必须创建用户名与密码，创建后禁止新增第二个账号，不支持多账号、注册、自助新增用户、角色与权限管理；后续启动需登录该本地账号，无远程认证、外部身份源或账号同步；忘记密码可通过首次创建时生成的一次性恢复码重设密码，恢复码只展示一次、由用户离线保存，使用后失效并生成新的恢复码。密码与恢复码不以明文存储，使用 Node 内置 scrypt + 每条记录随机盐 + 恒定时间比较，不引入原生密码依赖。
5. 应用在每日首次使用时，若当天尚无自动备份，自动创建一份备份；自动备份仅保留最近 7 份，更旧的自动备份被清理。
6. 支持负责人立即手动备份到所选本地目录；手动备份不受最近 7 份数量限制。
7. 支持从负责人所选本地备份恢复；恢复前需确认并验证备份可读，恢复失败不得覆盖当前数据。
8. 备份或恢复失败时给出明确错误提示，不静默视为成功。
9. 系统升级涉及数据结构变更时，通过数据迁移保留现有本地数据；迁移失败时保留可恢复状态，不静默丢弃或损坏现有数据。
10. 上述边界不规定具体数据目录、文件布局或数据库实现细节。
11. 本地账号仅为应用访问门槛，不加密 SQLite 数据库文件；Windows 操作系统账户仍是本机数据文件与备份的主要保护边界。登录本地账号不能防止直接读取数据库文件，文档不得声称登录可保护数据库文件本身。

## 13. 验收场景

以下场景均由已确认规则可直接验证：

1. **进单日期口径**：正式进单时进单日期必填，默认取当天并允许补录或修正；负责人填写的值不被当天默认值覆盖；待进单或未进单先执行阶段可空；进单金额按进单日期所属月份归属统计。
2. **向导步骤 1 基本信息**：新建项目向导步骤 1 展示进单日期、区域、旧址联系人、新址联系人、合同开始与截止日期，不包含项目负责人或销售通知时间；合同截止日期早于开始日期时拒绝保存。
3. **向导步骤 2 搬迁范围**：展示旧址地址、新址地址、仪器名称（必填）、型号（选填）、UPS 是/否，不展示 Ship-to 地址快照；未填写仪器名称时拒绝保存。
4. **向导步骤 3 执行准备**：计划上门日期与计划运输日期分开记录，并分别记录场地确认、实际装机完成日期与服务单号（选填）；留空字段保存时不无提示丢失；实际装机完成日期在执行前为空不触发状态流转或提醒。
5. **向导单号自动创建搬迁开单**：填写选填服务单号且已选定参与工程师时，项目与自动创建的搬迁开单记录同次保存，实际生成日期默认当天，备注可后补；填写单号但未选定工程师时拒绝保存整个向导并就地提示先补齐工程师；不填写单号时不创建开单。
6. **实际装机完成自动进入待验收**：录入实际装机完成日期后项目自动进入待验收；计划上门/运输日期到期或场地已确认不触发状态流转。
7. **主状态人工调整**：负责人可直接选择/调整项目主状态；系统校验合法状态与取消约束；人工调整不得覆盖"实际装机完成自动待验收、验收报告自动待掉票、金额闭环自动已完成/回待掉票"。
8. **未进单与已进单视觉区分**：未进单项目与已进单项目在界面使用明确不同的颜色/视觉标识。
9. **未进单先执行**：核心信息未齐且经经理批复后可优先安排上门；原项目标记"未进单先执行"并记录批复、原因及缺失项，主状态保持待进单；补齐后在同一项目完成进单，主状态由负责人人工确定。
10. **开单独立性**：开单与正式进单是两个不同业务事件，开单不影响进单状态与主状态；非空服务单号全局唯一。
11. **开单工作量**：同一服务单号无论关联多少名工程师或多少次上门，开单量只计一次，按搬迁、认证、单寄备件、PM 四类业务类型分组；认证/单寄备件/PM 开单至少记录开单日期、服务单号、开单类型、工程师、客户单位，备注可选，开单日期未填默认当天。
12. **批次与物流**：搬迁批次与物流费用合并为一次记录，批次创建同时必填费用登记日期（默认当天）、合同预算价与物流成交价（人民币，均必填且大于 0），运输公司可选；物流成交价即最终实际物流费用；物流成交价大于合同预算价时警告但允许保存；物流费用合同占比按固定汇率折算后除以最新合同 USD 含税金额，合同金额空/0 时不可计算并提示。
13. **Ship-to 不可变与申请线性状态**：Ship-to 创建后不可修改；目的地址变化时重新申请新的 Ship-to；申请只记录客户名称与新址地址，不关联搬迁仪器、不保存地址快照；Account ID 完成前必填、补入后全局唯一并进入已完成；状态线性流转待提交 → 处理中 → 已完成，不支持退回或取消；每条申请首次实际提交计一次工作量。
14. **序列号地址更新**：逐台登记更新事实（客户名称、新址地址、序列号、Account ID、更新日期），更新日期默认当天并可补录历史日期；提供列表与筛选并按更新日期所属月份计数；不创建、修改或删除不可变 Ship-to；序列号须与登记仪器一致。
15. **损坏维修单备件与备件状态**：一个事项仅含一个备件，同一损坏多个备件分别建立事项；事项记录备件申请日期与备件处理状态（待提交、处理中、已到件、已使用）；仅"已使用"备件计入维修费用与合同占比；备件金额保留 USD/RMB 原币，RMB 按 1 USD = 7.2 RMB 折算用于占比；合同占比 = 单条事项金额 ÷ 合同 USD 含税金额，合同金额为空或零时不可计算，占比超过 100% 允许显示并给出警告。
16. **合同金额为 0 时的维修限制**：合同 USD 含税金额为空或 0 时，可登记损坏，但禁止开始/完成维修、禁止将备件标记为"已使用"；补齐正数合同金额后才允许。
17. **二维码是否申请手工**：仪器"二维码是否申请"为手工是/否字段，不保存二维码地址、不由申请记录推导、不自动创建项目提醒、不阻塞上门、运输或项目状态流转。
18. **二维码申请独立模块**：每条申请记录申请人、申请日期与多选类型（九类固定代码）；工作量按申请记录 × 去重后的选中类型计数；不关联搬迁仪器或搬迁项目；不设状态流转；项目快速记录不含二维码申请。
19. **项目提醒手工维护**：负责人为每个项目手工维护一个当前提醒（提醒日期 + 备注），可编辑或清除、不保存完成历史；系统不根据缺失字段自动生成提醒；成交高于预算、Ship-to 申请未完成、二维码未标记等均不自动创建提醒；到期分类按提醒日期显示临期/今日到期/已逾期，临期窗口可配置、默认未来 7 个自然日；提醒仅在工作台内展示。
20. **取消规则**：无任何掉票历史（含已撤销）的任一未取消状态可取消（必须记录取消日期与原因）；存在任何掉票历史（含已撤销）禁止取消；已取消项目不可恢复、禁止修改金额与掉票，继续工作需重新新增项目；收入与掉票指标排除已取消项目，真实物流费用与备件成本保留并标记取消。**已转单**为与已取消同类的终态：由负责人人工进入，转单后不再自动推进、人工进入后不可再离开；已转单项目与已取消同等排除活跃项目、进单金额（收入）、掉票与项目管道统计，并同等冻结金额与掉票修改。
21. **金额规则**：金额两位小数、十进制定点、四舍五入、不得负数；仅合同 USD 含税金额允许 0，其他录入金额有值必须大于 0；合同金额为 0 时正式进单的最终可确认金额必须另行录入大于 0 的值；最终可确认金额不得低于累计掉票金额。
22. **合同金额直接覆盖**：合同 USD 含税金额可直接覆盖当前值修改，不保存正式合同变更对象/历史、不要求原因；进单金额快照保持原值；最终可确认金额保持原值、不随合同覆盖同步。
23. **掉票撤销终态**：掉票不可物理删除，只可撤销（记录撤销日期与原因）；撤销后为终态，禁止编辑、重复撤销或重新激活，更正需新增有效掉票；撤销后重算统计与状态。
24. **掉票闭环重算**：累计掉票金额达到最终可确认金额进入已完成；掉票修改、撤销或最终可确认金额修改后在待掉票与已完成之间重算；项目未处于待掉票或已完成时金额修改不改变主状态。
25. **迁移 ECC 聚合与整批事务**：迁移以 ECC 为项目/合同聚合主键，同一 ECC 下全部执行数据聚合导入并作为一个项目展示；缺 ECC 由 dry-run 报必填错误；重复非空服务单号进入冲突清单、解决前整批禁止导入；dry-run 对目标必填字段缺失输出源文件、sheet、行与字段错误；客户修正源 Excel 或通过补录模板补齐后重跑；正式导入前不得存在错误；每个批次整体事务、不部分导入，同源重跑不重复写入；可选字段可空；工作台无迁移与补录入口；导入时间只作审计字段，不替代源业务日期。
26. **报表筛选与导出**：月份区间由负责人手工选择（无默认季度），实时计算；支持导出 Excel（.xlsx）、图片（PNG）与 PDF，导出内容为当前筛选条件下的实时结果。
27. **客户名称唯一业务标识**：客户名称为去除首尾空白后全局唯一的唯一业务标识；同一客户名称可关联多个不同 ECC 项目；不记录客户外部编号。
28. **单一本地账号访问边界**：首次启动必须创建用户名与密码，创建后无新增账号、注册、角色与权限管理入口；后续启动需登录该本地账号，无远程认证、外部身份源与账号同步；忘记密码凭一次性恢复码重设（恢复码只展示一次、离线保存、使用后失效并生成新恢复码）；密码与恢复码不以明文存储（Node 内置 scrypt + 每条记录随机盐 + 恒定时间比较，不引入原生密码依赖）；本地账号不加密 SQLite，Windows 操作系统账户仍是本机数据文件与备份的主要保护边界；手工录入事实与工作量责任人归属当前登录账号，动作记录持久化账号内部 ID 与当时用户名快照，历史统计不因以后改名变化。
