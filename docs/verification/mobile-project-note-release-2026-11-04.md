# 手机项目备注与联系信息：v3 发布记录

## 范围与授权

2026-11-04，用户明确要求手机端展示项目备注、项目提醒信息、新旧址联系人和新旧地址，并在修改后上线。本次沿用既有 Basic Auth 查看权限与只读边界；不新增编辑、导出或公开分享。

联系人、地址、提醒日期和提醒备注已由 `0ea8df9` 的 [v2 扩展](mobile-readonly-detail-expansion-2026-10-27.md)提供。本次新增项目备注，不重复建立字段或修改本地数据库结构。项目备注与提醒备注可发布；开单备注、维修备注、取消/撤销/损坏/经理批复原因等其余自由文本继续排除。

## v3 封闭字段表

v1 与 v2 的字段表保持原样。v3 包含 v2 的全部字段，并仅增加以下字段：

| JSON 路径（相对上传体 snapshot） | 来源 | 类型及空值 | 用途 |
|---|---|---|---|
| `projects[].detail.projectNote` | `WorkbenchV2ProjectDetailDto.detail.projectNote` | `string \| null`，v3 必填 | 手机项目详情中的项目备注 |

- 新桌面仅生成 schemaVersion 3；新服务按 1、2、3 分版本严格校验。v1/v2 中出现项目备注字段仍非法，v3 缺少该字段也非法；未知字段及未知版本仍拒绝。
- `null` 或空串表示未填写。旧快照中字段缺失显示“当前快照未提供”，不能拿历史备注补入新快照。
- 字段在既有一致事务内逐项投影；项目备注只通过鉴权后的项目详情返回，不进入项目列表或上传凭证可读的非业务元数据。
- 手机保留长文本换行并安全转义，不将备注解释为 HTML。原有提醒日期/备注、新旧址联系人及地址继续显示。
- 成功发布基线必须同时匹配业务指纹与当前 schema 版本。已启用的旧桌面升级后，即使业务数据未变，也应发布一次 v3；成功后不重复，失败不推进，原本停用的发布仍保持停用。

## 上线与验收顺序

1. 用合成数据完成类型检查、移动端相关单测、构建与浏览器/发布端到端验证。
2. 核对生产服务目标、现行部署流程和回滚方式，保留已有凭证及快照，不输出业务内容或密钥。
3. 先更新支持 v1/v2/v3 的服务及手机页面，确认健康检查、未认证访问拦截和版本兼容。
4. 再更新真实数据源所在桌面端，沿用原发布配置生成 v3 快照。不得用合成快照替换生产数据，也不得把旧快照缺失字段伪造为已填写。
5. 用格式版本、字段存在性、计数或哈希验证实际发布结果，不在日志打印项目备注、联系人、地址等业务值。

服务更新本身不会补出旧快照缺失的信息；必须由持有本地业务数据的新版桌面完成发布。旧服务可能无法读取已落盘的 v3，回滚不得直接覆盖新快照或丢失已发布数据。
