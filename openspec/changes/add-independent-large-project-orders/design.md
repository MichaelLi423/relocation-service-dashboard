# Design

## Context

参见 `proposal.md`。当前 `ServiceOrderService.recordOrder` 将搬迁类型与项目 ID 强绑定，非搬迁类型已允许 `projectId=null`；现有 `service_orders.project_id` 可空，报表按服务单号和开单日期统计，独立记录在无区域/标签筛选时已能计入总量。工作台的开单表单目前只在项目上下文出现，客户单位从项目派生。项目列表、阶段指标和移动只读快照都会读取真实项目，因此不能用伪项目承载新工作量。SQLite 迁移使用 `PRAGMA user_version`，最新迁移为 v21，只能追加版本。

## Goals / Non-Goals

**Goals:**

- 用一条持久化且显式的工作范围标记区分中大型开单与其他开单，既有记录升级后绝不因 `project_id IS NULL` 被追认为中大型。
- 在同一条开单流水上沿用四类类型、唯一单号、客户单位、可空工程师及已有补录/删除能力，仅针对中大型搬迁开单放开项目关联要求。
- 工作范围过滤应用于月度开单量、明细和现有导出链路，而不改变其他项目或财务指标的项目归属。

**Non-Goals:**

- 不创建中大型项目、项目生命周期、合同、进单、搬迁进度或项目标签；不改动既有项目关联开单的项目查询语义。
- 不把中大型独立开单纳入只按搬迁项目采集的移动只读项目快照；独立记录的手机端浏览不在本次范围。
- 不将“开单一次”改为“每名工程师一次”，也不自动按服务单号推断项目范围。

## Decisions

### 1. 在开单自身保存工作范围，而不是造项目或复用开单类型

为开单记录增加受限的 `workScope`（例如 `other` / `medium_large`），默认 `other` 表示“非中大型或既有记录”，并非断言历史记录全部属于小型搬迁；由新独立入口显式传入 `medium_large`。迁移在现有 v21 之后**追加** v22，给现存行填 `other`，保留已有单号唯一索引、导入来源字段、修订触发器和工程师可空约束；同步更新仓储映射与共享读取契约。历史导入等未标记来源保持 `other`，不得根据项目 ID 空值反推工作范围。项目表和 `order_type` 四值 CHECK 不变。

相较增加第五种类型，正交标记保留原四类分组；相较内置项目，不必在队列、状态、统计、搜索、快照等多处增加排除哨兵。

### 2. 在领域边界验证范围与关联的一致性

沿用已有开单动作和主进程校验，允许独立入口发送无 `projectId` 的记录并显式提供工作范围。领域层拒绝未知范围、`medium_large` 带项目 ID，以及 `other` 的无项目搬迁开单；对有项目的其他类型继续验证项目真实存在。独立表单手工填客户单位；有项目的原表单继续从项目客户派生。工作范围与日期、类型、单号、客户单位、项目关联同属创建身份，不加入备注/工程师的原位编辑能力。共享 IPC / facade 不以“没有选中项目”代替 `medium_large` 的显式意图。

相较仅在 UI 限制，领域验证同时覆盖 IPC 的直接调用；相较新建独立开单表，复用记录及既有唯一索引和删除逻辑。

### 3. 入口独立，记录和报表沿用现有读取路径

顶栏“二维码申请”后增加独立按钮，打开不需要选中项目的开单表单；在原四字段上增加必填客户单位。可复用字段组件、保存反馈和键盘操作，但不复用会注入选中项目 ID 的项目快速记录提交上下文。保存后刷新跨项目历史和相关统计，无须刷新某个项目的 orders section；跨项目历史展示工作范围以辨认，不产生伪 ECC/项目编号。

报表筛选增加 `workScope`，只约束开单量指标；默认不选则包含全部记录，选择 `medium_large` 只纳入显式标记，选择 `other` 纳入既有及非中大型。先按同一组筛选构建明细，再生成四类分组计数、下钻与 Excel/PNG/PDF 导出，避免页面与文件出现不同口径。区域/项目标签属于项目维度：一旦选择，`projectId=null` 记录在该指标、下钻和导出中一致排除；界面说明中大型独立记录不适用此类筛选。

相较新增独立统计模块，这保留现有报表与服务单号计数规则，也减少导出路径分叉。

## Risks / Trade-offs

- [仅靠可空项目关联推断中大型会误标历史非搬迁独立开单] → 使用持久化的显式范围和默认 `other`，覆盖升级与导入回归测试。
- [区域/标签与中大型筛选同时选中时得到空结果，易误解] → 在筛选附近说明独立开单没有项目区域/标签，指标、下钻和三种导出执行相同交集规则。
- [绕过界面通过 IPC 伪造范围或项目关联] → 在领域层验证交叉约束，并测试无项目普通搬迁被拒、无项目中大型四类可保存、带项目中大型被拒。
- [迁移及历史读取遗漏字段导致已有记录丢失或显示错误] → 追加迁移测试（v21→v22 和新库）、仓储/历史/报表端到端用例，并保留现存唯一索引与导入默认口径。

## Migration Plan

追加 v22 迁移，不改历史迁移。升级存量库时给开单填 `other`；新库依序执行迁移得到相同形状。升级不会生成项目或重写旧服务单，回退到旧应用版本不作为就地数据库降级方案；需要回退时先使用既有备份/恢复机制恢复升级前数据库。发布前用合成数据验证迁移、唯一约束、历史展示和报表口径，不读取或更改客户敏感源表。
